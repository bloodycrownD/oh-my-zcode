# CHANGELOG 撰写

面向用户的更新说明——用户在 GitHub Release 页看到的内容（CI 会把对应版本段落原样写入 Release 正文）。写 changelog 时**站在用户视角**，不暴露内部实现细节。

## 输入

从下列来源汇总本批改动（用户会指定其中部分或全部）：

- 当前迭代文档（`docs/iterations/<name>/`，本仓 docs 在 omz/ 之外：`D:\Dev\Js\oh-my-zcode\docs\iterations\`）
- 工作区 diff / commit 历史（`git --no-pager log --oneline <base>..HEAD`、`git --no-pager diff <base>..HEAD --stat`）
- CR fix-spec（`cr-fix-spec.md`）——但 **fix-spec 是内部实现质量记录，不是用户可见 changelog 条目的来源**；只用于理解"这条修复到底修了什么用户可感知的问题"

**禁止**把 fix-spec 的编号（uix/B-1、mc/A-1、e2e/R-2 等）、内部术语（P0/P1、C-orch、wave、guard、tracker）、模块路径、类型名写进 changelog。用户看不到这些。

## 分类规范

[CHANGELOG.md](../../../CHANGELOG.md) 分四类（`###` 小节）：

| 分类 | 含义 | 判断标准 |
|------|------|----------|
| **新增** | 用户获得了之前没有的能力 | "现在可以做 X 了" |
| **修复** | 修复了用户实际遇到 / 可感知的 bug | "之前 X 不工作 / 报错 / 行为异常，现在修好了" |
| **变更** | 用户可感知的行为或界面变化 | "X 的表现 / 展示变了"（不是 bug，是刻意调整） |
| **维护** | 内部重构、测试防线、可观测性、架构调整 | 对用户行为无直接影响，但记录让维护者知道改了什么 |

## 核心原则

### 1. 一个功能只在一个分类出现

不要把同一功能拆成"主功能在新增、实现细节在变更、内部收尾在维护"三段。维护段写的是**独立的内部改动**（纯重构、测试防线、死代码清理），不是某个用户可见功能的实现细节。

**判断方法**：写完一条问自己"这条和上面那条是同一个东西吗？"——是就合并。

### 2. 不把开发过程中引入又修复的 bug 写进「修复」

同一批改动引入 + 修复、用户从未在正式版本体验过的问题，不写进修复——用户看到"修了 X"会以为之前有这个问题。

### 3. 内部术语转人话

> ❌ 修复：uix/B-1 outputLimitDetected 死标志导致自然退出超限不截断
>
> ✅ 修复：失控命令输出撑爆磁盘——上限收紧并自动截断保留头尾

### 4. 面向"做了什么"，不是"怎么做的"

描述结果和用户价值。实现细节留在 commit message / spec / fix-spec 里。

## 撰写流程

1. 汇总改动（按"输入"节来源）
2. 归并同一功能的子项
3. 按分类表归入唯一一类
4. 每条转成用户视角的人话
5. 写入 `## [Unreleased]` 段（发版时由 [omz-publish](../omz-publish/SKILL.md) 挪到具体版本号）

## 版本段格式

```markdown
## [x.y.z](https://github.com/bloodycrownD/oh-my-zcode/compare/v上一版...vx.y.z) (YYYY-MM-DD)

### 新增
- **简短标题**：一句话描述用户可感知的变化——补充一句必要上下文。
```

粗体标题概括要点，破折号后补充上下文。compare 链接的上一版取最近 tag。

## 校对清单（写完逐项过）

- [ ] **无重复**：同一用户可感知的行为只出现一次
- [ ] **无内部细节**：无 CR 编号 / P0P1 / 模块路径 / 类型名 / helper 名
- [ ] **无过程 bug**：本批引入又修复的问题不在「修复」段
- [ ] **维护段覆盖**：独立内部改动有记录（某功能的实现细节不算）
- [ ] **面向用户**：每条是"能看到 / 体验到什么"
- [ ] **无错别字**：通读一遍
- [ ] **无裸美元符**：条目不出现裸露 `$` / `$$`（markdown 渲染器可能当公式定界符；必要时用文字或确保包在反引号内）
- [ ] **措辞简洁**：一条一两句讲完，不铺陈实现
